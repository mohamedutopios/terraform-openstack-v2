Modules versionnés par tags, avec CI

README.md — un dépôt et un pipeline par module ; l'infra épingle les versions et a son propre pipeline

Avant / après

Ce que ça apporte

  • Une version = un code figé : l'infra sait exactement ce qu'elle déploie.
  • Chaque consommateur monte de version quand il le décide.
  • Le module est testé, documenté et scanné une fois, pour tous.

Ce que ça coûte

  • Un dépôt et un pipeline de plus par module.
  • Monter de version est un geste explicite (changer ref, relancer init).
  • Les tags doivent être protégés pour rester fiables.

Plusieurs environnements : dev, staging, prod

DEMO-ENVIRONNEMENTS.md — un dossier, un backend, un état, des identifiants et des versions par environnement

Avant / après

Ce que ça apporte

  • Un destroy en dev ne peut pas toucher la prod (autre état, autre compte, autre projet).
  • La CI de dev ne reçoit jamais les identifiants de prod.
  • Les écarts entre environnements se lisent dans un diff de dossiers.

Ce que ça coûte

  • La composition est répétée dans chaque envs/<env>/main.tf.
  • Un socle à appliquer une fois (projets, comptes, quotas).
  • Trois variables d'identifiants à gérer dans GitLab.
